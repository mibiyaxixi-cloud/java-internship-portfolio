# 演示稿（约 7—10 分钟）

这是演示方案，不是本轮已录制视频。M2 图表点击和浏览器下载的交互验收仍因浏览器管理策略校验故障待补；接口、构建、数据库验证有证据，准备对外展示前按末尾清单亲自演练。

## 开场（约 30 秒）

“这是模拟小型连锁门店的订单与经营报表后台。我已有预约候补项目，这个项目侧重 CSV 数据质量、数据库事务、统计口径和查询分析。它使用独立 MySQL，订单是不可变快照，没有真实支付和部分退款。”

## 按顺序展示

1. **登录与范围（1 分钟）**：启动方式按 README。管理员登录，展示全部门店选择。不要把 .env 密码放到投屏或截图中。
2. **导入与错误（2 分钟）**：选择 `database/demo-orders.csv`，说明 5 行、4 单、两个商品；如果已导入，会返回原成功批次。需要展示初次确认时，在本地复制文件并给四个订单号加同一个新后缀，日期改为另一个明确的演示范围，之后保留它们，不清库。故意把一行金额写成三位小数，预检查会显示行号和原因，整批不写业务订单。修正后确认，再传同文件证明不重复。
3. **原订单与口径（1 分钟）**：打开 DEMO-A，100 元有两行，9/30 支付、10/1 退款；解释为什么原支付日销售不能因为当前 REFUNDED 状态而消失。
4. **报表与下钻（2 分钟）**：点“演示日期”。全部门店两日销售 200、退款 100、净额 100；9/30 为 140，10/1 净额 -40。点退款或表格日明细，查看 DEMO-A 两个退款商品共 100 元，打开原始订单。
5. **导出与权限（1 分钟）**：导出资金事件 CSV，两日共 6 行，销售/退款/净额合计一致；台账金额为原单金额，不能当净销售。退出后登录 store1，只应看到 CS01；不要只说“前端隐藏了其他门店”，说明服务器在列表、报表、导入和导出各入口检查范围。
6. **SQL 证据（1—2 分钟）**：打开 performance.md 与原始 JSON，说明 50,000 单/100,000 明细来自可复现模拟 CSV，真正通过业务导入到测试库。比较原索引扫描 4,173 行和新索引 20 行；本机列表中位 3.31 → 0.19 ms。强调是特定稀疏退款筛选、暖缓存、单客户端，不能当线上容量指标。

开发库已有固定演示数据，不需要为了演示重复删除数据。M3 基准仅写测试库，生成的 BENCH_M3 文件不能直接上传到开发库（对应门店/商品也只在测试夹具中存在）。

## 命令行备选证据

```bash
./scripts/backend.sh verify
API_BASE=http://127.0.0.1:5174/api node scripts/smoke.mjs
API_BASE=http://127.0.0.1:5174/api node scripts/smoke-m2.mjs
./scripts/benchmark.sh
```

最后一条单独运行，勿与其他测试并行。HTTP 脚本固定核对原演示日期；如果添加了同日期订单，金额变化是真实结果，不要清空用户数据让断言通过。

## 演示前自查与讲解边界

- 重新登录，亲自核对图表、下钻、下载、账号切换和窄窗口布局；当前的浏览器工具故障不是这些行为已经通过的证明。
- 能指出 ImportWriter 的事务边界、BatchTransactions 的独立失败事务、数据库唯一键、身份如何进入筛选 SQL。
- 能解释订单台账日期与报表事件日期不同，为什么不用 `SUM(DISTINCT total_cents)` 消除 JOIN 重复。
- 只把实际理解和修改过的部分作为自己的经验；开发方式、独立完成程度按真实情况说明。

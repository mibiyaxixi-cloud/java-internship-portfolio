# M3：从查询条件到索引，再用证据判断

## 关键 SQL

实际分页 SQL 与完整计划见 [performance.md](performance.md)，对应 `OrderMapper.list`。它按门店、状态等值过滤，按下单时间做半开范围过滤，连接 stores 主键取得门店名，最后按下单时间和 ID 倒序取 20 行。

```sql
CREATE INDEX ix_store_status_ordered_id
    ON orders(store_id, status, ordered_at, id);
```

为什么这个次序有用：先定位一个门店的一个状态，再读日期区间；日期和 ID 同方向倒序可使用反向索引扫描。ID 用来保证同一时刻的订单也有稳定顺序。门店主键 JOIN 一对一，不用 JOIN 明细，也不会放大整单金额。

原 `(store_id, ordered_at, id)` 已避免额外排序，但退款只占 0.5%，仍要扫描很多订单后判断 status。首轮计划实际读 4,173 行才拿到 20 条退款，新索引只读 20 行。不要说“原来全表扫描”或“消除了 filesort”：原计划有索引，也没有 filesort。count 也受益，但无状态过滤仍要保留原索引；新索引不自动解决全门店报表或深分页。

先看字段、过滤和排序，再比较 EXPLAIN 估计与 ANALYZE 实际行数，再多次计时。单次最快值、估计 cost、生成的数据量，都不能单独证明生产性能。结果没改善时也要保留记录，不靠 FORCE INDEX 把计划改成预想的样子。

## 一次完整数据流

用户打开本店退款订单列表 → Session 对应账号在服务端解析为当前 storeId → OrderService 校验日期/状态/分页 → MyBatis 绑定参数生成真实 SQL → MySQL 在新联合索引定位范围并连 stores → 返回分页行与 count → 前端展示原始订单。

本阶段的验证沿着这条流反向检查：固定公式生成 20 份受限 CSV → 正常预检查/确认导入独立测试库 → 确认 50,000 单/100,000 明细及整单合计 → 提取真实 Mapper SQL → 记录前后计划、样本与结果一致性 → 按本次身份清理夹具 → 将有证据支持的索引写入 Flyway V3 → 全回归与开发服务启动验收。
